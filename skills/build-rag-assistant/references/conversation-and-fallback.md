# 多轮记忆、通用知识兜底、对话日志治理

> 对应正文:**层 8 / 9 / 10** + **跳过可见性**。讲"怎么记住上下文、本地没有时怎么兜底、怎么埋可观测"。

## 层 8:多轮记忆

最近 N 轮(如 5 轮)**按用户**持久化(localStorage key 带 userId),作答时带 `history` 给 LLM 消解追问指代("它 / 上面的 / 那个药")。
- 历史要**瘦身**:取最近几轮(如 3 轮)、每条内容截断(如 300 字),减小喂给 LLM 的 prompt;
- 否则多轮越问越慢(历史膨胀拖慢作答,尤其中长上下文模型第 2 问起延迟陡增);
- 注入 history 时只接受 `user` / `assistant` 两种角色,防异常 role。
> **这是业务问答(问答式、对话深度有限)的标准做法**,绝大多数 RAG 助手够用。只有你的场景是**长对话 / 陪伴式**(几十轮、跨多主题、需长程指代消解)才需要记忆摘要(summarization)、实体记忆(entity memory)、向量化的 episodic memory——那是**高级对话管理,属进阶,本 skill 不展开**;别为一个"问完就走"的业务助手提前背上这套复杂度。

## 层 9:通用知识兜底(可选)

本地 0 命中、且非计数/规模问题 → 回退模型通用知识作答,前端显「通用知识 · 非本平台数据」标识。
- 约束**不臆造平台专属数据**(具体库存 / 营业额 / 某网点详情 / 某机构内部信息)——通用知识无从得知,如实说"我暂无该数据"并引导去业务页;
- **光靠 prompt 说"别臆造平台数据"不够可靠**(LLM 不知道你的业务边界,会把通用知识里撞名的药名 / 机构名当真)。但**别把整张名词表塞进 prompt 让 LLM 自己匹配**——几千专名全进 prompt,token 成本和延迟陡增;只给高频又漏低频专名(LLM 臆造最危险的恰恰是它"知道"的撞名实体);而且让 LLM 自己判匹配,本身就违背本 skill 的确定性原则(它不可靠地遵守指令)。**两个更稳的做法**:
  1. **默认:强约束 system prompt + 低 temperature + 硬边界**——通用兜底 `mode=general` 下,prompt 明确"只答通用知识,**不就任何具体平台实体的属性作答**;涉及具体平台数据一律回『我暂无该数据』"。零额外 token、确定性最强,代价是偶尔对撞名概念过度拒答(误伤 < 臆造的代价)。
  2. **若要专名硬拦截,走后端确定性后处理,不靠 LLM**:LLM 通用兜底答案产出后,后端拿名词表做**确定性的多模式匹配**(像拒答检测的 `contains`),命中平台专名 → 拦截或标红。最小实现:
     - **名词表来源**:从主数据表(药品 / 网点 / 机构)拉取,定期或按变更事件同步,别手维护;
     - **匹配用子串 / AC 自动机,千万别先分词**——中文专名匹配**不能先分词**(会把「阿司匹林肠溶片」切碎、漏匹配变体),用 **Aho-Corasick** 一次扫描全文命中所有专名:既容变体(子串命中)又比模糊相似度少误伤;
     - **误拦截率评估**:上线前拿一批历史通用兜底 query 跑一遍看误伤率(撞名被误拦的),太高就加白名单或收紧(如要求「专名 + 具体属性词」共现才拦,单提专名不拦);
     - 这把"可执行边界"做实,又不费 prompt token、不赌 LLM 可靠性。**别因为"难实现"就退回纯 prompt**——文档已警告光靠 prompt 不可靠,退回去等于白警告。
- temperature 可比 RAG 分支略高(如 0.5);
- ⚠️ `mode=general`(通用知识标签)**只在"本地 0 命中且非计数问题"时**才置——作答 API 异常走 `mode=error`,绝不混入通用兜底(见 `providers-and-stack.md` 的「作答异常 ≠ 通用兜底」)。

## 层 10:对话日志治理(第一天就埋)

每条提问落库:`requestId / query / answer / hitCount / flagged / flagReason` 等(`requestId` 与检索诊断日志共享,见 `vector-store.md`)。异常规则标记:
- **无效提问**(垃圾话 / 越界)、**0 命中**、**高频**(同用户 10 分钟 > N 次)、**重复**(同用户同问 10 分钟 ≥ M 次);
- **`flagReason` 用固定枚举码,别自由字符串**(`invalid / out_of_scope / zero_hit / high_freq / duplicate / error`)——否则后期 `GROUP BY flagReason` 聚合分析会因文案飘忽而失效,等于白埋;
- **越界抑制 0 命中**:越界问题的来源是被清空的显示产物,不应记成"0 命中"(否则污染覆盖率统计)。

> 这套日志是后续调 prompt / 调 min-score 门槛 / 看覆盖盲区 / 发现刷量的**唯一依据**,第一天就埋,别等"以后再说"。

### 从日志到看板(进阶,可选)

对话日志表 + 检索诊断日志本身就是观测源,**不用另起一套**:把 `flagged / flagReason / hitCount / mode` 接 Grafana(或任意 BI)出几个核心面板。**两个数据源别混**:业务质量指标(0 命中率 / 越界占比 / topN 未命中 / mode 分布)从**对话日志表(SQL 聚合)**算;性能指标(检索延迟 / 作答延迟 / 错误率)从 **metrics(PromQL)**算。

核心面板 query 样例(对话日志表,字段:`mode / flagReason / hitCount / query / ts`):
- **0 命中率**:`SELECT sum(flagReason='zero_hit')/count(*) FROM kb_log WHERE ts BETWEEN $__timeFrom() AND $__timeTo()`;
- **mode 分布**:`SELECT mode, count(*) FROM kb_log GROUP BY mode`;
- **topN 未命中 query(覆盖盲区)**:`SELECT query, count(*) c FROM kb_log WHERE flagReason='zero_hit' AND mode!='out_of_scope' GROUP BY query ORDER BY c DESC LIMIT 20`(排掉越界垃圾话,只看正经却没答上的);
- **错误率**:`SELECT sum(mode='error')/count(*) FROM kb_log`(性能更准的话走 metrics 的 `http_server_requests_seconds`)。

结构化日志(见 `vector-store.md` 诊断日志)是这一步的前提。OTel 链路追踪属平台级进阶,中小助手不必上,日志表够看。

> **日志轮转 / 归档 / 保留不在本 skill 编排范围**——走你**现有的日志运维**(logrotate / 容器日志驱动 / Loki 保留期);对话日志表本身按下面「安全 / 合规基线」的保留窗口定期清理。

## ⚠️ 安全 / 合规基线(声明层,生产必补)

本 skill 默认假设**受控内网业务系统**(查询方是登录用户、知识库是内部业务数据)。**生产化前必须显式补这一层**,别 silent skip:
- **日志含敏感数据**:`query / answer` 可能落进 PII、具体业务数字(库存 / 营业额)、患者信息——落库前按字段脱敏(或只存摘要 / hash,排查时凭 requestId 回溯),别整条明文长期留存;
- **保留期**:按合规定(GDPR / 等保 / 行业规),对话日志不是无限保留,设保留窗口 + 定期清理;
- **LLM 输出后端审核**(可选):涉政 / 涉敏 / PII 泄露,作答返回前过一道审核闸(规则或内容安全 API),命中拦截;
- **越界提问本身**:高频 / 重复越界提问可能是探测攻击,日志 `flagged` 标记后值得**单独告警**,不止于统计。

> 这一层的**实现不在本 skill 范围**(取决于业务场景 / 合规要求),但必须**显式声明"已知、待补"**别当不存在——见下面的「跳过可见性」。

## 跳过可见性(必做)

本 skill 的层是完整骨架。若某层这次不做(如不做多轮、不做通用兜底、不做日志治理),**输出里必须显式声明"跳过了层 X,因为 Y"**。
- silent skip = 看不见的缺口(下次谁来都不知道这层没做);
- declared skip = 可审的决策(可追踪、可补)。
