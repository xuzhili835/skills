# 向量库选型、scope 隔离、建库与检索

> 对应正文:**决策先定** + **层 1 / 2 / 3**。讲"向量存哪、怎么行级隔离、怎么建库、怎么检索、min-score 怎么调"。

## 选型:应用内存检索 + 关系库存档(别上重武器)

几百~几千文档规模,**不需要独立向量库**(Pinecone / Milvus / PG-Vec)。够用的方案:
- 向量以 JSON 存关系库一张表(`id, vector, scope`),应用就绪时加载回内存;
- 检索在内存做**暴力余弦**(毫秒级、几 MB),和纯内存方案一样省;
- 重启不丢(关系库存档)。

> **量级感觉(自己估一下,判断要不要换)**:一条 1024 维 float 向量 ≈ 4 KB;N 条 ≈ N×4 KB 常驻内存(1 万条 ≈ 40 MB)。检索 = N 次点积 ≈ N×1024 次浮点乘加:5000 条 ≈ 500 万次运算、现代 CPU 约 **1~5 ms**;5 万条 ≈ 5 亿次、约 **10~50 ms**,开始逼近下面的判定线。**先用这个估算你的规模,再对照多维判定线决定要不要换**——别凭"文档数"拍脑袋。
>
> ⚠️ **上面是纯运算理论值,实际生产更高**:没算 GC 停顿(Java / Go)、内存访问 / cache miss(5 万条 ≈ 200 MB 遍历有开销)、并发竞争(多请求同时检索)、向量冷启动(首次加载)。所以**别照理论值卡线**——保守起见 **1~2 万条就压测验证**(真实延迟 / p95 / 并发下表现),到了就考虑独立向量库,别硬撑到理论 5 万条。

### 升级到独立向量库的判定线(多维信号,别只看文档数)

单一文档数门槛(如"到 1 万就换")偏死——真实瓶颈是下面任意一条命中,才值得引独立向量库:
- **检索延迟**:单次召回稳定 > 50ms(暴力扫描随向量数线性增长,这是最直接的信号);
- **内存占用**:向量常驻内存**挤压应用堆 / 业务缓存**——不看绝对 MB(2G 机和 16G 机标准不同),看"向量占用相对应用堆的占比",如占堆 1/3 以上、开始挤占业务缓存就到线;
- **多实例共享**:需要跨进程 / 多副本共享同一份向量(单实例内存方案无法共享);
- 文档数只是上述信号的**间接代理**(几万条以下、单实例,通常一条都不命中)。

> 判定顺序:先看延迟 → 内存 → 是否多实例;都不命中就别引——多一个依赖多一份运维,对中小知识库收益是负的。

> 参考实现:MySQL 存档 + 进程内 `ConcurrentHashMap` 检索。向量须 **L2 归一化**,使余弦退化为点积(检索只算点积,最快)。`@ConditionalOnProperty` 在"关系库存档"与"纯内存(测试用)"间切。

## 层 1:scope 行级隔离(安全底线,不是优化)

先定义租户 scope:`GLOBAL` / `ORG:id` / `USER:id` 之类。**检索前过滤、绝不检索后过滤**:
- `ScopeResolver.visibleScopes(user)` 返回该用户可见 scope 集合;
- `search()` 把它做**前置过滤条件**——只对可见 scope 的向量算余弦。
> 坑:检索后再过滤 = 先把别人数据召回再丢,既慢又在日志/缓存层泄漏。scope 必须是检索**入参**。

## 层 2:自动建库(seeding)

优先从**已有业务表**生成知识文档(药品 / 材料 / 政策 / 组织主数据…),切块→嵌入→入库,一键重建。
> 别一上来做"用户上传 PDF"——业务系统里 90% 的知识已在表里,先把它变可问答的。
- 切块:size ~500 字符、overlap ~60(防边界丢句);
- 内容去重:同内容 hash 命中已建索引则跳过,避免重复嵌入计费。

### 增量更新(别只会全量重建)

全量 seeding 只够冷启动;线上知识会变——**新增一条 / 改一条 / 删一条**都要能增量同步向量,否则知识库停在导入那天。按业务表的 CUD 钩子(或定时对账)做:
- **新增 / 修改**:业务行落库后,对该行重新切块 → re-embed → 按 `docId` / `chunkId` **upsert**(同 id 覆盖旧向量);改了内容的行,旧 chunk 向量必须**整组替换**(按业务行 id 删旧再插新,别留半截新旧混读)。
- **删除**:不物理删向量,先**软删标志**(`deleted=1`),检索时过滤跳过——保留可追溯;后台再批量清理。
- **版本号**:每条向量带 `sourceVersion`(业务行 `update_time` 或版本字段),增量扫描只处理版本号变了的行,避免全表重嵌。
> 增量最容易翻车的是"新旧混读":改了业务行却没 re-embed → 检索仍命中旧向量、作答基于陈旧内容。落地后必测:改一条业务数据 → 立即问 → 答案是否反映新值。
> **删后同 id 重插**(业务行删除后又用同 id 插入新内容):软删按 `(业务id, 版本)` 标记、新插入带**新版本号**;检索过滤 `deleted=1` 天然不命中旧向量,不会"新旧并存"。软删行会堆积——**按保留窗口定期物理清理**(如软删超 30 天的向量行直接删;软删对象就是向量行本身,清理即删这些行,没有额外"关联 chunk"要处理);**别用业务 id 当向量主键的唯一判据**,用 `(业务id, version)` 复合,否则重插会撞到软删的旧行。
>
> **触发方式(按规模 / 实时性三选一)**:
> - **定时对账**(默认,中小用这个):扫 `update_time > 上次扫描点`,解耦、容忍短时不一致,每分钟级;
> - **实时钩子**:业务行 CUD 后同步 re-embed,延迟最低、但**耦合业务写路径**(嵌入调用塞进业务事务,慢或失败拖累业务写);
> - **异步索引队列**(高实时 + 想解耦):业务 CUD 只**投事件到消息队列**(Kafka / RabbitMQ / Redis Stream),**独立索引 worker** 消费 → re-embed → upsert。业务写路径零耦合、近实时(秒级)、可独立扩缩 / 重试。中小是过度设计,但知识每几分钟变、又不想耦合业务写时是正解。
>
> ⚠️ **只扫 `update_time` 的三个漏洞 + 补法**:
> 1. **删除捕获**——业务行删除时 `update_time` 不变(甚至行没了),光扫它**漏删** → 改用**变更日志表(changelog / CDC)**记 CUD 事件,或业务侧软删标志(`deleted`)扫描,定时任务读变更流来同步向量软删;
> 2. **批量导入漏扫**——夜间 ETL 大批量写入,若跨扫描周期或时间戳同秒,分钟级扫描会漏 → **批量导入结束后触发一次全量对账兜底**(按版本号 diff 全量重算,和定时增量互补);
> 3. **并发版本冲突**——向量与业务行用乐观锁,写入带版本号、冲突重试,避免并发修改导致向量落后于业务行。

## 层 3:检索 + min-score 门槛

`query 嵌入 → 余弦 top-k(已按 scope 前置过滤)→ min-score 过滤弱命中 → 回表取块文本 + 得分`,按相关度降序。命中片段**编号 `[1][2]`** 供作答引用。

### min-score 调参实战(语义嵌入下的坑,最容易调错)

1. **门槛的真正职责是挡垃圾话,不是减少命中数**。语义嵌入(bge-m3 等)下:垃圾话/无关 query 余弦通常 **0.30~0.37**,沾边内容 **0.40~0.55**,强相关 **0.55+**。把门槛设在垃圾话与沾边之间(如 **0.40**)即可正确挡掉垃圾话——否则垃圾话会满 topK、冒充命中、被当成正经问题作答。
   > ⚠️ **0.40 是 bge-m3 的经验值,别照搬到别的模型**:不同嵌入模型分数分布不同(如 OpenAI `ada-002` 余弦更集中、绝对值偏高,0.40 在它那儿可能太低)。换模型**必须重测门槛**——跑一批已知相关 / 不相关的 query 看 scores 分布,重新定门槛,别直接套 0.40。
2. **绝对阈值有天花板,别指望靠调高它打破"满 topK"**。语义嵌入会把"沾边"内容压缩在 0.45~0.55 窄带、且与强相关分数接近。把门槛拧到 0.55 想减命中,会把**正经沾边问题直接砍成 0 命中**(误伤→变通用兜底,体验更差)。门槛挡住垃圾话就够了,不必追求"满 topK 变 2/3"。
3. **要减少"满 topK"的冗余,靠动态手段,不靠绝对阈值**:
   - **同文档去重**:同一篇文档切出的多个 chunk 常霸占 topK 名额(query 沾边一篇就召回它的好几块)→ 同 `docId` 只保留最高分一条,来源更多样、名额不被一篇占满;
   - **分数断崖截断**:若 topK 内相邻分数有显著落差(如 0.65→0.54),在落差处截断,保留强相关、丢弃突降的弱命中。
4. **hashing(stub)嵌入下 min-score 意义弱**:hashing 是词面重合非语义,中文高频字让大量文档余弦虚高,门槛几乎筛不掉东西——它只用于未接真实模型时跑通管线,别拿它调门槛。

### 检索诊断日志(必埋)

检索时打印 `query | minScore | 候选 topK 分数(含 @docId) | 过门槛保留数`,例如:
```
kb retrieve q='住院报销' minScore=0.4 scores=[0.733@12,0.662@12,0.544@8] kept=3
```
- 分数看区分度、`@docId` 看是否同文档霸占名额——这是调门槛、决定要不要做同文档去重的**唯一依据**。没有这条日志,min-score 调参全靠猜。
- **结构化是日志框架层、不是字符串里塞 JSON**:文本格式(`kb retrieve q=... scores=[...]`)走人读的 sink;结构化走**另一条 sink**——用日志框架的 MDC 字段或 JSON line formatter 把 `q / minScore / kept / scores[{docId,score}]` **分字段**输出,别拼成一个含 JSON 的字符串(那样既不像人话、机器也难解析)。两条独立 sink,不混在一行。
- **带 requestId 串联回话**:每条提问生成一个 `requestId`,**检索诊断日志和对话日志(见 `conversation-and-fallback.md`)都带上它**——排查时用 requestId 把"这次提问的检索 scores + 命中数 + 作答 mode + 异常"串成一条链,而不是各自孤立的行。
