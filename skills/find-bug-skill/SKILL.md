# 找业务 bug：托管式独立测试 → 固定格式报告

被要求"找 bug / 测一轮"时，**不问怎么做，直接做完整套并交报告**（配合 autopilot 姿态）。核心纪律三条：

1. **"能跑" ≠ "业务正确"**——断言业务规则，不是 HTTP 200。
2. **两种运行模式，以用户的明确指令为切换条件**：
   - **审查模式（默认）**——听到"找 bug / 测一轮 / 我去睡了你自己测"这类话就是它：产出报告，交出即止，一行代码不动；
   - **修复模式（须明示进入）**——只有类似"把报告里的 P1-2 修掉""这些问题全部修复"的直接指令才算数。进入后守三条契约：**范围以报告编号为合同**，点名哪几条修哪几条，不顺手扩展（入口是用户口头报障直接点名修复、尚无报告时：先逐条复现实锤、按报告格式补录成 P? 编号再修，合同以补录后的编号为准；没能复现的如实标注"按描述修＋加防御"）；修复中撞出的新问题自动升级为本轮新发现，照常记录并回归；每条修完固定三件事——复跑该条原探针见绿、在校准单标注为已修的回归探针、对相邻受影响逻辑做回归抽查。
   同一对话里从审查切到修复属于开启新任务；拿不准用户意思就问一句，禁止猜成大开闸。
3. **环境是你自己拉起来的，就要还回去**——开始前拍基线快照，结束后对账还原。

> 消歧：UI 照样触发（有头浏览器），不是跳过 UI；区别在断言对象是"规则成不成立"，不是"按钮能不能点"。

## 步骤

### 0. 环境自举 + 基线快照（约 5 分钟）

- **先画像，再动手（这条保证本 skill 不绑技术栈）**：正文出现的拉起序列、表名、脚本全部只是**示例**；换项目先自己做环境画像——组件怎么构建、逐个怎么拉起、真正的对外入口是什么（统一网关？各服务直连端口？CLI？）、持久化状态落在哪（哪种库/文件/队列）——画像清楚后，后续所有步骤原样适用。
- **领域边界声明**：本 skill 执行层假设为 web 形态（HTTP API / SQL / 浏览器 UI）。非 web 对象（数据管道、桌面/CAD 插件、算法/训练链路）复用第 1、2、5 步的纪律与报告骨架，"三层验证"按目标系统重写实例（例：算子或脚本入口 / 输入模型与数据文件 / 输出结果与落盘产物），有头浏览器、网关/token 等 web 专属段落作废，缺哪层在覆盖声明里写明——纪律不换，皮换。混合形态（浏览器壳 + WebSocket/长连接、无 HTTP API/无 DB）不按例外处理：按实际通道逐层归类即可，并给自定义协议补一类探针——两端消息契约一致性（字段名/语义对不上、半死通道静默吞消息，均有真实案例背书）。
- **旧账先翻**：到被测项目仓库找上一轮攒的《回归校准单》与主干冒烟单（通常在项目根目录，见文末配套脚本节）——存在就先跑冒烟单确认主干还活着，再**通读校准单**，里面每条探针都是本轮必配项，不是参考资料。
- **端口摸底**：看服务起没起（Windows `netstat -ano | grep LISTENING` / Unix `lsof -iTCP -sTCP:LISTEN`）。用户的服务在跑→**不要动用户的进程**，确认代码版本新旧即可；全没起→按上面画像用**待测的最新代码**自己拉全套（示例：某 Spring Cloud 项目的序列是注册中心→逐个微服务→前端 dev server），全部后台运行。
- **基线快照**（后面还原全靠它）：
  - DB 各表行数（主数据/订单类/日志类一张 SELECT UNION 搞定）
  - 关键表结构核对（迁移版本对不对、新列在不在）
  - 有副作用的第三方配额（如外部 API 额度）记下来，测试全程避免消耗。
- **可达性声明**：API 层 / DB 层（直查对账）/ UI 层（有头浏览器）。缺哪层必须在报告里写明原因，不许哑跳。

### 1. 先读 ground-truth 的**源码形态**，再设计用例

- 需求/设计文档定义"应怎样"；没有就从领域推导并声明假设。
- **接口形状从 DTO/Schema 源码读，别猜**：请求字段名、校验注解矩阵、错误码枚举的分段。凭猜测写的用例会把"自己传错参"当 bug。
- **实时渲染应用（游戏/canvas/3D）先做可达性审计**：页面上下文能否拿到内部状态（实体/相机/动画器/弹道）？拿得到→状态/几何探针全开；拿不到→降级为"console 日志＋截图"双通道并在覆盖声明写明。三层归类、探针骨架与节拍单见 `references/game-probe-playbook.md`（被测对象含实时渲染时必读）。
- 权限真相通常分散在**两层**：入口侧的路由/角色白名单（实例：API 网关过滤器的路径角色表）和服务层的 requireLogin/requireAdmin 式守卫——**两处口径不一致本身就是高危 bug 类别**（例：入口把 `/report/**` 整体划管理员，服务层却只要求登录 → 普通用户功能整个不可用）。
- **枚举入口要通道用尽**：可用来源不止一处——控制器路由、OpenAPI/Swagger 文档、网关路由配置、前端路由表、框架装饰器全局 grep、浏览器从页面菜单爬可达面——全部查过才算穷尽。从中挑闭环走到底（内容平台如 认证→上传→审核→发布；交易系统如 认证→下单→支付→退款），一条流走到底比逐页点按钮更能抓跨模块 bug。多角色闭环时，为闭环里**每个角色各建一个独立登录会话**，全程用各自的 token 操作与断言、按跳切换视角，不共用一个账号。**所有通道穷尽仍画不出业务流地图时**，如实把"入口不可发现"写进覆盖声明未测项（并提示该系统可测性差），禁止硬编造一条流程充数。
- **用例先行（流程步矩阵）**：动手执行前，把选定闭环逐步拆成用例矩阵，每行五列——**①前置/依赖**（依赖前面哪步的状态，如退款依赖支付成功）；**②操作 + 测试数据**（探针与输入，边界值/超长串/坏数据在此列名目）；**③断言四层**（API 响应 / DB 状态 / UI 可见 / 异步触达，涉哪层写哪层）；**④类别标注**（步骤 2 的断言类别与步骤 3 的对抗项挂到具体步骤，如"token 四连"挂登录步、"重复提交"挂下单步）；**⑤结果**（执行后回填通过/问题编号）。矩阵随报告附上：执行者照单施工不漏项，审查者开跑**之前**就能看到"打算测什么"，跑完即得"流程 N 步 ↔ 用例 M 行"的覆盖对账，未覆盖步显式写原因。

### 2. 每步断言业务规则

逐类查（每类都要有用例，不只 happy path）：
- **一致性/台账**：计数真涨了？派生值服务端算？关联表和聚合数一致？
- **隔离/所有权**：建两个普通账号 + 一个管理员，所有"自己的资源"操作互相打一遍越权矩阵（改/删/加/私有读），全部应拒绝且消息统一。
- **状态机**：合法转移走通，非法转移（已发布再重提、驳回态直接过审……）逐个断言拒绝理由正确。**合法的反向分支同样要端到端走完**：取消/拒收/超时自动关单，每条都走到底，终点断言库存回滚、资金退回、双方视图同步退场——正向主干走通 ≠ 闭环完成。
- **信任边界**：客户端上报值（时长/数量/价格）负数、超大、0 全试；禁用/改密后旧 token 是否当场失效。
- **守卫一致性**：A 路径拦了的行为，B 路径拦没拦？（例：前端强制必填的字段，裸调后端 API 绕不绕得过——**前端强制 ≠ 后端强制**，永远用裸 API 重放一遍绕过 attempt。）
- **校验顺序 vs 运行时开关**：带开关的分支每个取值遍历一遍，被关分支不该报参数错。
- **错误码不撞车**：不同失败因单独造用例，验"以正确的理由拒绝"，返回码各不相同。
- **单点坏数据 vs 全局**：列表/搜索/批量操作里混一条坏数据（外部来源解析不了的条目、缺资源的记录），整体不能挂——要么跳过要么降级。
- **状态可见性矩阵**：角色×状态×入口列表三方齐验——新提交的资源要在"我的+待审队列"出现、不能提前漏进公开列表；禁用账号的资源要从共享列表退场。（只看 API 返回不够，对应页面入口也要真看得见。）
- **异步触达**：闭环里每一处"对方应该收到消息/通知"，必须以**接收方身份**验证——用其 token 查消息列表接口或直查消息表确认真的落了行；发送方返回 200 不算数。撤回后不可见、未读计数增减也归这类。
- **派生/反规范字段的重算时机**：封面图、计数、榜单这类缓存值，新增、删除、换源三条路径都要触发重算——"取最新一张带图的当封面"这种规则，把那张图的主人删了之后还成立吗？
- **改名/引用关键字级联**：改了名称/标题后，所有按旧名过滤、搜索、归属匹配的地方逐个重走；引用型字段（如选择已有实体）不应静默新建重复行。
- **外部内容落地规范化**：多来源抓来的标题/文本，入库前繁简、裁剪、空白的口径要统一——每类来源各采一条真实样本断言终态（如第三方字幕整篇繁体、视频平台原始长标题直接入库，都是这类真实 bug）。
- **边界清空类**：已有值的字段遇到"新的为空"时应该保留还是清空？（专辑封面遇无封面新歌被清空就是这类真实 bug。）状态的三种走向都要跑。顺带查编辑弹窗：打开要完整预填现值，"只改一个字段"提交不得把其余字段清掉或用旧值顶掉。

### 3. 对抗面清单（除上述外固定要打的）

- **身份伪造双探**：经网关伪造内部信任头（应为拒绝，验证剥离）；直连内部服务端口同头（预期通过=内网信任模型成立，写进报告提醒部署不得暴露内网口）。
- **token 生命周期四连**：登录→改密→旧 token 应拒；管理员重置后同理；禁用后存量 token 应拒且禁用期登录拒；解禁重新登录正常。（秒级宽限是常见折衷，断言时 sleep ≥1.3s 再动。）
- **畸形输入**：非法 JSON 体、字段类型错（int 字段给字符串）、超长串、SQL 注入式关键词——后者不应 500。
- **闲置自发请求探针（11-04 实战补入）**：进入页面后**不做任何操作**静置 10~15s，观察是否自行发出请求或自行弹错。第三方 SDK/组件的 failover 回调若缺"本次动作由用户发起"的闸门，会替用户发请求：真实案例=验证码 SDK 内部请求 Network Error 后 8s 调 `success(占位票据)`，页面直接 `POST /api/auth/login`（账号密码空串）→ 后端 Bean Validation 回 400 → toast "password 不能为空"，用户什么都没做就看到字段报错（答辩首屏即受损）。打点法：进页面前 monkey-patch `XMLHttpRequest.prototype.open/send`（或 fetch）记录 url+body，同时挂 MutationObserver 收 toast 文本；判定=请求体为空/占位参数 且 无真实用户点击（事件 `isTrusted=false` 或无点击记录）即立案。
- **单侧起服务矩阵**：把依赖按"只起前端不起后端 / 只起后端不起前端 / 第三方全断"各跑一次**冷启动**（不是"已登录时后端重启"，冷启动是另一个面）；逐条记录首屏看到什么文案。判据：报错文案是否指向真实原因（"网络异常"对，"password 不能为空"错——后者说明有后端在真校验，用户对"后端没起"的判断需要现场复核）。
- **幂等/重复**：重复加条目、重复收藏/取消、重复提交、后台任务去重（连点应复用同一任务而非堆积）；后台任务/列表接口要经得住轮询风暴，反复刷不偶发加载失败。
- **代理度量**：榜单/推荐数字若建在可刷的埋点上，试刷一下就知道服务端校没收口。

### 4. 跨层验证

- **API**：脚本 fetch 直打入口（UTF-8 天然正确）；**GET 请求禁止带 body**（undici 直接抛 TypeError）；查询参数手动拼 querystring。
- **DB**：响应 200 但库状态错仍是 bug——状态位、计数、关联行直查对账。
- **全链路优先于抽检**：UI 层执行顺序 = 每个核心角色先把主闭环在真实界面里**完整走一遍**，逐步断言三件事——按钮点击有可见反馈、背后状态真改库、提交中按钮禁用/防重复点击（双击防重不许只在 API 层测）；六类抽检用于闭环走不到的页面。
- **全角色 × 全页面矩阵（不许抽检）**：只要系统有角色菜单，就必须**按角色展开所有可达路由逐屏过**，一屏一张截图 + 一次交互断言，报告里给"角色 × 页面"对账表。实测教训（11-04）：管理员 10 页全绿，但巡查员/专家/修缮端因菜单裁剪从未被打开过，真 bug 恰恰藏在那边；同一 bug 在四个页面重复（下拉框）也是靠矩阵才数清的。角色切换必须**整页加载**（`location.href=`）而非 `pushState`——SPA 的 store 只在应用启动读 localStorage，pushState 会让"新账号登录了、界面还显示旧用户"的假象骗过审查（本人踩过，差点误报成产品 bug）。
- **UI 抽检**（有头浏览器；带呼吸动画的按钮自动化会因 not stable 超时，用 `--force`）。不是随便点点，固定六类动作各来一遍：①弹窗真能走完闭环——有按钮、点了真改库（改密码弹窗只有壳就是典型实锤)；②浅色/深色主题各过一遍重点页，遮罩/覆盖层别糊死内容（计算样式可用 `getComputedStyle` 断言）；③切走再切回，watch 不带 immediate 会丢动效丢状态；④全局状态一变，所有消费组件都得跟（顶栏与底栏不同步是实锤）；⑤表单里的开关/选项拨下去必须有可观测差异，两个选项完全等价、勾选无效都是 bug；⑥**视觉合理性截图走查**——每个关键页截一张图问自己"页面上展示的东西和背后的数据相符吗"：图片字段渲染的是真图还是占位大字/裂图、表格有没有合理铺满页面而不是挤成一小块、空态/加载态存在且得体。"功能正常但用起来不正常"就是 bug。参照系是 **Nielsen 十大可用性启发式**，不是个人审美：系统状态可见、贴近真实世界、用户可控可逆、一致性与标准、防错优于报错、识别而非回忆、灵活高效、极简美学、错误可懂可恢复、按需帮助。十条能收敛掉大部分分歧，剩余的主观余量统一记观察项。走查中发现的"这样设计合不合理"记进报告观察项，不当场拍板。
- ⑧**选择器选项探针（不是看接口 200，是点开数选项）**：逐个点开每个 `<select>`/`<el-select>`/下拉/单选组，断言 `选项数 > 0` 且 `每项文本非空`。实测教训（11-04）：接口返回 200、页面也不报错，但**下拉里是 2 个空选项**——分页响应 `{total,list}` 被直接塞给 `v-for`，遍历对象正好产出 2 个 undefined 项。判据：选项数恰为 2 且文本全空 → 高度疑似"分页对象当数组用"；任意一屏如此即立案，再 grep 所有同类调用点（一个 API helper 通常被多个页面复用，一处坏往往四页全坏）。顺带核 `:key` 是否全 undefined——这是同一根因的更早信号。
- ⑨**切换重播与静态快照两连**：①**动画重播**——同一页面来回切两次，若入场动画（`opacity 0→1` + `translateY` + 级联延迟）每次都重播，用户感知是"内容框忽大忽小/在跳"，记易用性问题；量化法：切页前后量内容容器宽度与 `animationstart` 次数，先排除真实布局抖动（容器宽度恒定=不是布局问题，是动画）。②**静态快照 vs 已有接口**——`grep -r "from '@/config/" src/views` 列出所有静态数据源，逐个核后端是否已有同源接口；**后端就绪而前端仍读写死快照**是典型静默不一致（新增一条数据、页面永远不出现，且没人报错）。实测教训（11-04）：落地页读 10 条写死坐标，后端公开接口早已返回真实数据——用户问"新增之后落地页会不会被影响"，答案是会。③**跨页面骨架一致性**——用户说"切来切去感觉框忽大忽小"时，先别急着归因动画：逐页量**标题区高度 + 内容首元素 top 偏移 + 首容器宽高 + 卡片数量/尺寸**，做成表格横向比对。判定=多数页面同值、个别页面偏离 → 那个页面漏了统一封装（真实案例：9 页都是 `page-wrap > page-head + el-card`，唯独建筑档案是裸 `<div><el-card>`，标题和工具栏一起包进卡片里，`pageHead.height` 为 null、包裹范围与其他页完全不同）。同时核**标题重复**：全局 header 若渲染当前页名、页面内又有同名 `<h2>`，同屏会各出现一次（截图能看到），改成"分组 / 页面"层级即可。这类"功能全对但观感不统一"属于易用性轴，按 Nielsen「一致性与标准」立项，不归到个人审美。
- ⑦**实时渲染走查**（游戏/canvas，与状态/几何探针配合，节拍单见 playbook）：默认节拍（出生/移动/跳跃/交互/攻击/受击/死亡/UI 开关）每拍截图＋拉 console 日志。四纪律：**问题驱动截图**（每张必带具体问题，如"枪应挂右手骨骼、枪口朝前"，不做开放问答）；**参照锚定**（规则来源优先级：用户参照＞仓库文档＞显式声明的假设）；**两遍确认**（可疑→换角度/拉近重拍→才报）；**视觉提议、探针定罪**（纯截图发现记观察项"存疑"，有几何/状态探针佐证才立 P?-n）。无参照可锚的观感类（手感/步态质量/"像不像"原作）不可自动化，写进覆盖声明，不硬判。

- ⑩**异常态探针 + 注入两坑（11-04 实战，必守）**：
  ①**改造网络层先认清客户端**：axios 在浏览器走 `XMLHttpRequest`，patch `window.fetch` 对业务页**完全无效**——本次实测 patch fetch 后点"查询"毫无变化，差点误判成"前端查询失败静默吞错"；真因是请求根本没被拦住。要拦业务请求就 patch `XMLHttpRequest.prototype.open/send`，并在 send 里手动 `Object.defineProperty(self,'readyState',{value:4})` + `dispatchEvent(new Event('error'))` 造失败；只有直连 `fetch` 的模块（自写的 SSE/流式接口）才 patch fetch。
  ②**注入脚本里的中文会乱码**：Git Bash → `base64 -w0` → `eval(atob(...))` 这条路上，中文字面量进页面后变成 Latin-1 乱码，凡用中文选择器/正则挑元素（`/发送/`、`/查询/`）都会**静默匹配不到**（本次两次"按钮没被点到"皆因此，还误以为产品有问题）。改用**索引定位**（`querySelectorAll('button')[0]`）或 `new TextDecoder().decode(Uint8Array.from(atob(b64),c=>c.charCodeAt(0)))` 先还原中文再比对；填输入框用原生 setter + `dispatchEvent(new Event('input',{bubbles:true}))` 让 Vue 收到。
  ③**异常语义探针**：对只允许 PUT/DELETE 的资源发 GET、对不存在的路径发任意方法，期望 404/405。回 500 说明全局异常处理器把框架异常兜底吃了——实测 `GET /api/repair-requests/{id}` 返回 500 而非 405（`GlobalExceptionHandler` 漏接 `HttpRequestMethodNotSupportedException`），会让排查方把"方法用错"误判成"服务端崩了"。同批要核 `/nonexistent-xyz`、`/资源/99999` 是否**正确** 404，以区分"兜底全错"与"只漏一类"。
  ④**异常态验收**：断网/后端停机时，长任务要有**明确文案 + 可重试入口**，不能只留空白 loading；`el-loading-mask` 是否解除要显式断言（残留遮罩=永久假死）。判据分级：文案对但无重试=观察项（说清哪个分支不可重试），文案错或空白=立案。

- ⑪**"本地好、线上坏"专查 + 降级分支必走（11-04 实战）**：用户说"线上这样、本地看不出"时，先别改代码，按这四条对账。
  ①**静态资源前缀**：dev 的 Vite proxy 往往带 rewrite（本仓库 `/uploads` → `/api/uploads`），生产 nginx 少这条 → 图片全 404，而本地一切正常。查法：看 `vite.config.js` 的 `proxy.rewrite`，再去线上/本机直接 curl 两种前缀（`/uploads/x.jpg` vs `/api/uploads/x.jpg`），200/404 一比即定案；库里存的是相对路径、服务端 context-path 又在变，这类"存的值 ≠ 可访问的 URL"是高频坑。
  ②**滚动层级探针**：量 `documentElement.scrollHeight` 与 `innerHeight`——相等=**窗口不滚**；再沿祖先链打印每层 `overflow/height/scrollHeight/clientHeight`，找出真正在滚的那一层。若窗口不滚而内容在 `.el-main` 里滚、主从列表再滚一层，用户感知就是"最大的滚动条没了、还专门做了个小滚动条"，属易用性缺陷（不是审美）。同时量短页卡片高度与下方留白（本次实测 589~689 高、留白 200~250px），一起作为"没填满"的证据。
  ③**第三方 SDK 的降级分支必须走一遍**：登录/验证码这类 SDK 除了"成功路径"，还有 **failover/占位票据** 路径。查法：跑一次真实流程并**读控制台 + 抓报文**——我们自己的 `console.warn` 往往就写着"已忽略/已降级"，但**这条日志本身可能是错的**（见 ⑫）。判据：任何"降级后仍需用户再操作一次"的路径都算 UX 缺陷，除非降级本身就是拒绝服务。
  ④**演示数据口径**：种子里的占位词（"示例市""XX 路"）在验收场景会显呆；同一字段的取值维度要齐（保护级别只有 省级/市级/一般不可移动文物，缺国家级/县级，且第三档与前两档不同维度）。这类不判 bug，记观察项并给出"改种子要新增迁移、别改已发布迁移"的落地路径。

- ⑫**别自造"第三方故障"判据——先抓报文，再让服务端裁（11-04 实战，代价：错判了一整轮）**：
  代码里凡是"检测别人坏了没"的自制启发式（长度阈值、字段像不像、正则猜格式），都可能在**对方完全正常**时把它判成故障，而且失败方向通常很危险：判成"降级"就静默跳过校验/丢掉票据。
  这次的实例：`isPlaceholderTicket()` 用"`certifyId` 长度 < 16 即占位票据"，而阿里云 V3 真票据的 `certifyId` **只有 10~11 位**（`{certifyId:"2qoowZVm1o",sceneId,isSign,securityToken}`）——每个真票据都被判成"SDK 降级"丢掉，后端票据缺省又跳过验签（fail-open），用户被迫点两次登录。我照着日志写下"SDK 反复回退占位票据"的结论并写进回执，**把错的根因传播给了其他线**。
  正确查法（30 分钟就能定案）：
  - **看那一条网络报文**：DevTools/`playwright-cli requests` + `request-body`/`response-body`。本次 `InitCaptchaV3` 明明返回 `{"Code":"Success","CertifyId":"2qoowZVm1o"}`——一眼就能否掉"SDK 不可用"。
  - **拿真回执直连服务端**：把票据原样 POST 给后端（真票据 `code:0`、伪造票据 `400 人机校验未通过`），两边一通，"是谁判错了"立刻清楚。
  - **判据只留结构标记**：只认对方显式给的标记（`failover===true`）和"根本没有票据"，别用长度/形态猜；有疑问就**把票据交给服务端裁**——服务端拒绝是可解释的错误，前端自作聪明放行是漏洞。
  - 日志里自己写的"降级/已忽略"是**假设**不是证据；写进报告/回执的根因必须能被一条报文或一次请求复现。

### 5. 清残留、还原基线

事务硬删所有测试实体（含连锁表与审计日志按时间戳裁剪）、删除落盘文件、必要时还原被测对象被改的字段。最后重新跑第 0 步那张 UNION 对账，一行都不能差。**停掉自己拉的全部进程**，用户原有常驻服务不动。

## 已知工具坑速查（真实踩过，勿再踩）

- Git Bash 里 curl -d 带中文 → 按 GBK 发送，服务端拒 UTF-8 报 Invalid start byte，**伪装成系统 500**。一律用 node fetch 或 `--data-binary @utf8file`。
- node 写 `/tmp/x.json` 在 Windows 实际落在 `C:\tmp\`（盘符映射）：脚本内用 `import.meta.dirname`。
- Reactive 技术栈（WebFlux 等）：事件循环线程里 `.block()` 抛异常会被 catch 吞掉 → **静默 fail-open**——吊销检查这种安全逻辑必须保持纯响应式链（这是真实发生过的失效模式：改完上线自测全绿，对抗探针一打就穿透）。
- 处理响应前先从源码确认拦截器剥了几层 data，以及 list 形状是 `list` 还是 `records`（同项目不同接口都可能不一样）。
- bash 双引号里 `/reg|exp/` 会被路径转换弄坏，find --regex 尽量用纯文本或转义。

## 配套脚本与回归校准单

- `scripts/api-harness.mjs`：node fetch 测试助手骨架（call/login/gjson/wait/ok）。复制到临时目录 `import('./h.mjs')` 即用；其中 login() 的端点和响应形状按你的项目改三行即可，fetch 助手的模式是通用的。
- `references/calibration-template.md`：**回归校准单模板**。用法按两个时间点执行，这是流程的一部分，不是可选项：
  - **开工前**（步骤 0）：找到该项目已填的校准单，通读并把历史每类坑纳入本轮探针计划。
  - **收尾时**（交报告的同时）：把本轮**新确认的问题**（含只测未修的）按"症状 → 最小复现探针 → 兜住的规则"追加成行；若用户已让修复，随手把它标注为回归探针。
  **填好的校准单永远放被测项目的仓库里**（建议项目根目录，和测试报告放一起），不放本技能目录——它绑定项目内部细节，留在项目里随仓库走；技能本体保持通用。修复合入后，它就是该项目最快的冒烟回归单。
- **主干冒烟单（收尾必产）**：把用例矩阵中全绿的主干步骤序列单独存档（放项目根目录与校准单作伴，报告"已验证正确的逻辑"节引用）。下轮开工顺序：先跑冒烟单确认主干活着，再上对抗探针——校准单管"以前坏过的地方"，冒烟单管"主干还活着"。

## 条款准入（防膨胀的刹车）

想往本技能加新条款时，先过三道闸，过不了就不许加：
1. **归轴**：把想法映射到 ISO/IEC 25010 的八大量纲（功能/性能/兼容/易用/可靠/安全/维护/移植）。只有落在**已入册轴**（当前为：功能逻辑、信息安全对抗、易用性抽检）上的新失效模式，才允许写进步骤 2/3；
2. **证据**：即便在册轴，新条款也必须有真实缺陷背书——本技能在某项目抓到过、或公开缺陷库高频出现。纯想象中的风险不收（检查清单行业通例：从事故长出来，不从头脑风暴长出来）;
3. **去重**：落笔前先对照公开目录（OWASP WSTG、ISTQB 测试设计技术、可用性启发式），别人已总结的直接引用思路不另造词。
被三道闸拦下的想法去向：报告的**未测项**或**观察项**，永不进入本文件。测试永远不完备——本技能的目标不是完备，是把每一次"想到还有没测的"转化成账面上一行显式的未测声明，而不是焦虑。

- ⑬**权限矩阵要"三角对账 + 闭环断层"，别只验 403（11-05 实战，漏报一次）**：按角色跑一遍"该 403 的 403 了"只证明**权限位**对，证明不了**分工合理**。补三轮：
  ①**三角对账**：设计文档的菜单矩阵 / 后端 `@RequireRole` / 前端路由守卫，三份摊开逐行比。任一处不一致就是缺陷（本案：EXPERT 施工验收——文档 §1.2 留空、§1.3 说可读、后端列表放行详情 403、前端无入口，四处各不相同）。
  ②**闭环断层**：站在每个角色的业务流程上问"我这一步做完，下一步该看见什么"——申请人在施工/验收阶段看不看得到结果？施工方拿不拿得到"按什么标准修"？这类"接口都通、就是有人瞎着"的缺口，端点级测试永远测不出来（本案两处：申请人在 DONE 之前全程失明、施工方只有一张缺陷图）。
  ③**文档本身可能是错的**：403/200 与文档一致≠合理。判据换成"业务是否说得通"：同为技术闸口，管理员能复核缺陷却不能出专家意见＝不对称；管理员能点结项却没有补记录权＝兜底形同虚设。**文档错了就改文档**（升版 + 写清判据），别把错误矩阵当成验收标准。
  落地顺序：先拉三份矩阵 → 找不一致 → 逐个问"这一步谁该看见什么" → 结论分成"改代码"与"改文档"两摞，后者当次改掉并升版。
  ④**先看界面把入口给了谁，再读注解**：`@RequireRole` 只是"接口允不允许"，**不等于"这个角色做不做得到"**。注解比 UI 宽 → 是**冗余接口**（拿 token 能绕过 UI，如巡查员可调结项接口自巡自结）；注解比 UI 窄 → 才是**功能缺失**（界面有按钮、点下去 403）。反向错误也要防：把"防呆校验拦住了越权操作"误判成缺陷——被 409/403 拦下且文案说了原因，往往正是设计意图，先问"这一拦是否合理"再定级。
